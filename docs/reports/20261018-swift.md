# Swift code audit, 2026-10-18

Scope: `Sources/PlayawayCore` (5.2k lines), `Sources/LocalPlayer` (Mac app, 4.3k), `Sources/PlayawayLyrics` (0.5k),
`ios/App` (iPhone and iPad, 3.3k), against the Swift 6 concurrency model, API design and the project's own rules
(CLAUDE.md: no magic numbers, no allocation in the audio path, platform parity). Tests (16k lines) and UI tests (1.6k)
were surveyed, not reviewed line by line.

## How this was done, and what it does not cover

- A survey by search of concurrency and safety markers in every target (counts below).
- A **strict-concurrency build** of the SwiftPM targets (`-strict-concurrency=complete`, separate build folder). It
  gave 188 distinct warning sites. The iPhone and iPad app is built by Xcode with its own setting and was **not**
  covered by that build. Its findings are from reading, in the iOS section below; its strict-concurrency warning
  count was **not measured** (a build is an instrument, not a requirement of an audit, and one was started for the app
  and stopped as unnecessary).
- Targeted reads of the hot spots named below.
- Not done: a line-by-line review of all 13.5k lines, a performance profile, memory or leak analysis, an accessibility
  review, a dependency audit (Sparkle, WhisperKit), and any run on a real device. "Verified" below means seen in the
  code or in a build, not observed on a device.

## Findings in detail

### 1. Swift 6 mode is off (High)

Every target builds with `swiftLanguageMode(.v5)` and the Xcode project says `SWIFT_VERSION "5.0"`. The data-race
checks Swift 6 adds are therefore silent. Building the package with complete strict concurrency gave **188 distinct
warning sites**, none in the iPhone app (not part of that build) and all but four in the Mac app:

| File | Sites |
|---|---|
| `Scripting/AppActions.swift` | 30 |
| `Open/NoticePresenter.swift` | 26 |
| `Playlists/PlaylistDocument.swift` | 21 |
| `App/UICheckMode.swift` | 16 |
| `App/LaunchCoordinator.swift` | 16 |
| `UI/WindowEnumerator.swift` | 15 |
| `App/AppDelegate.swift` | 12 |
| `Updates/SparkleConfigTest.swift` | 11 |
| `PlayawayCore/UI/TransportViewModel.swift` | 4 |

The dominant messages are "main actor-isolated property can not be referenced from a nonisolated context" (about half
of 432 emissions; each site is emitted more than once) and "call to main actor-isolated method in a synchronous
nonisolated context". They are almost all one root cause: the Mac types are `@MainActor` and are called from places the
compiler cannot prove are on the main thread (callbacks, `Timer`, `Combine` sinks, `NSDocument` overrides). The
core, which has no isolation at all, produces few warnings only because it declares no isolation to violate.

Recommendation: move the shared core to Swift 6 mode first (it is the smallest, 4 sites, and has no UI), then the
iPhone app, then the Mac app file by file starting with the three biggest (`AppActions`, `NoticePresenter`,
`PlaylistDocument`). Keep the Mac on 5 until it is clean; do not flip it with the warnings standing.

### 2. Restore listed the whole tree on the main thread (High, being fixed)

`RecoveryPlanner.apply` listed the entire chosen folder recursively, always, and was called synchronously from the
chooser's callback. On a large iCloud tree (cloud-only directories are fetched as they are listed) that blocks the
interface for as long as the listing takes. The owner reported a hang on the iPad and "looks broken" on the iPhone.
Fix in progress, test first: songs at their saved place are checked directly with no listing (the common case), the
tree is listed only for the rest, in the background, with a count of files looked at, a visible progress overlay and a
Cancel button. New core tests: no listing when nothing moved, one listing otherwise, progress counts only grow,
cancel keeps what was found.

### 3. Adding a song reads its audio header on the main thread (High)

Story 41 made `TrackReference.make(for:)` record a duration by opening the file with `AVAudioFile`. Adding songs from the
file chooser runs that for every file, synchronously, on the main thread (`PlaylistSession.add` -> `adding` ->
`makeReference`). For a file iCloud has not downloaded this can block on, or start, a download. It also makes adding a
300-song folder pay 300 file opens before the list updates. Recommendation: record size at add time (cheap resource
value) and fill duration later in the background (the design already allows the field to stay nil), or read duration
off the main thread. A test: adding a placeholder file must not open it.

### 4. One shared rule, two designs (Medium)

The Mac resolves a playlist's files on a global queue and applies the results on the main thread, dropping any result
whose reference changed meanwhile (`PlaylistDocument.resolveStatuses`). The iPhone resolves per row, on the main
thread, while the row is drawn, and caches it (`songURLs`). The project's principle is to share behaviour and keep
adapters thin; this is behaviour that differs, and the iPhone's version is the one that hangs under load. Recommendation:
move the Mac's snapshot-then-apply resolution into the core and use it from both.

### 5. `AppModel` (Medium)

26 published properties, 98 functions, 1,290 lines, and 279 lines of test hooks (seeds, fake chooser, churn timer)
inside `#if DEBUG` in the production file. Several defects this month came from state shared inside it (the restore sheet's session lost when the sheet closed; the folder-grant notice firing on
the wrong device). Recommendation: extract the restore flow, the cloud and download handling and the debug hooks into
their own types; keep `AppModel` as the composition root.

### 6. Core classes assume the main thread without saying so (Medium)

`TransportViewModel`, `PlaylistPlayer`, `AVPlaybackEngine` and the two stores are plain classes with mutable state and no
isolation. They are only safe because every caller is on the main thread, which the compiler cannot check and a
background caller (as `resolveStatuses` is, for the resolver) could break. The nine `MainActor.assumeIsolated` calls in
the iPhone app, and the Mac's `DispatchQueue.main` hops, exist to bridge callbacks into them. Recommendation: mark the
playback classes `@MainActor` in the core (the `AudioExclusivity` and `NoCopiedPlaybackState` scan tests already
assume one thread), then delete the bridging.

### 7. Blocking sleep in `LoopingPreview.stop()` (Medium)

The fade out sleeps the calling thread five times (about 10 ms in total) so the loop's volume steps down before the
engine stops. The caller is the main thread. It is short, but the project rule is no blocking in the audio path and
the scrub loop bug the owner reported is in this area. Recommendation: fade with the audio engine's own ramp or a
scheduled volume change rather than a sleeping loop.

### 8. Test hygiene (Medium)

48 fixed `Thread.sleep` calls and 118 `try!` in tests, plus `sleep(1)` in UI tests. Fixed sleeps are slow and flaky;
`try!` turns a failing setup into a crash that hides which assertion was meant. Recommendation: replace sleeps with
the existing `spin`/expectation helpers and `try` with `XCTUnwrap` or a throwing test.

### 9 to 12 (Low)

- `@unchecked Sendable` on `WhisperKitTranscriber` and `MDXNetSeparator`: both hold model state and are used from a
  detached task; not reviewed for real thread safety. Document the invariant or move the state into an actor.
- `LyricsPipeline` is the one real actor in the project and is used correctly.
- The Mac's three `RunLoop.main.run` loops (waiting for downloads and results in `AppActions`) are intentional (an
  AppleScript command must return a value) but are the reason those methods cannot be `async`.
- Magic numbers: named constants exist for most timings (`pollInterval`, `stallTimeout`, `handoffFade`); the exceptions
  listed in the table should follow suit.
- The three `as!` are on `NSDocumentController` results that the app itself installs; `fatalError` appears only in
  `required init?(coder:)` of programmatic views, which is the standard idiom.

Recommendations, in this order: split the restore, cloud-download and debug code out of `AppModel` (I5, I9, finding 5);
replace the download timers with the system's change notifications where they exist (I4); migrate `AppModel` and
`PlaylistSession` to `@Observable` one property group at a time (I1); keep the UIKit table, since SwiftUI's `List` only
reorders in edit mode and the product wants press-and-hold, but test drags under change (I2, a test for it was added
this session; it passed in the simulator, so the owner's failure is not yet reproduced); re-evaluate `CardSheet` against
the iOS 26 sheet APIs before the next OS release (I3).

## What is good

- The shared core is genuinely platform neutral: no UIKit or AppKit, `package` access, tests run in seconds.
- Concurrency uses few primitives: one actor, no locks, no semaphores, no `nonisolated(unsafe)`.
- Cancellation and generation counters guard stale background results (`refreshGeneration`, the Mac's reference check).
- Long operations in the core take injected seams (`FolderListing`, `CloudRoots`, file operations), which is why the
  restore bug could be reproduced and tested without a device.
- Test discipline: source-scan tests enforce the audio-exclusivity and no-copied-playback-state rules.
